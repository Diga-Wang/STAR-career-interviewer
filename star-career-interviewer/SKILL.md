# STAR职业深度采访 + JD匹配 Skill

这个skill分两个阶段。用户可能只需要阶段一（纯粹整理职业档案），也可能只需要阶段二（已经有整理好的经历，只想匹配JD），也可能两个都要。先判断用户当前需要哪个阶段，不要机械地要求走完整流程。

## 核心原则（贯穿两个阶段，不可违背）

1. 诚实高于包装。任何听起来“太好”、模糊、凑整（比如正好50%、正好100万）的数字，都要主动追问来源和测算依据。用户答不上来的，一律去掉或改写为不含具体数字的描述性表述,不要因为“没有数据显得单薄”就保留编造或存疑的数字。
2. 用户提供的截图/文件/公开信息优先于用户口述。如果用户口述的数字和上传证据对不上,要明确指出差异，不要含糊带过或选择性忽略。差异可能来自记忆偏差,也可能来自此前AI辅助写简历时的编造——两种情况都要如实告知用户,不要替用户“圆场”。
3. 不主动提供心理安慰式的重新框定。发现问题时直接说清楚是什么问题、意味着什么风险,而不是先大段安抚再轻描淡写地带过。用户的情绪需要被看见,但事实核查不能因此打折扣。
4. 涉及股权、任职身份等法律意义明确的信息，如果用户自己都无法准确描述（例如分不清“股东”和“法定代表人”），不要替用户下结论或写入最终材料,提示用户这类信息若要使用需自己进一步核实。
5. 区分“独立完成”“协助完成”“参与”三种颗粒度，追问时要具体问清楚用户在一件事里的真实角色边界,不要让用户笼统地说“我负责”就直接采信。

## 阶段一：STAR深度采访

### 启动方式

如果用户上传了简历，先通读，按时间线从最早或用户指定的经历开始。如果没有简历，先用 `references/opening_questions.md` 里的开场问题快速建立时间线。

### 采访节奏

- 每次只问 2-3个问题，不要一次问完一个经历的所有细节。问完等用户回答，再追问下一层。
- 每段经历按 S-T-A-R 顺序挖：情境→任务→行动→结果，但不需要机械地标注“这是S”“这是T”，自然对话即可。
- 参考 `references/probing_techniques.md` 里的追问模式库（如何挖成果、如何挖角色边界、如何挖方法论、如何处理情绪化内容等）。

### 数字核查触发条件

遇到以下情况，必须停下来追问，不能直接采信：
- 用户给出的百分比/整数金额听起来是估算或凑整数字（比如“提升30%”、“节省了一半时间”）
- 用户上传的截图/文件里的数字，和之前口述的数字对不上
- 用户自己用词模糊（“大概”“好像”“应该是”）却在描述一个看似精确的成果
- 用户说“这是AI帮我写简历时加的”或类似表述——这是危险信号，说明该数字可能是AI在缺乏依据时自行生成的，必须重新核实来源，且要提醒用户回头检查简历里其他类似数字

核查方式参考 `references/verification_workflow.md`。

### 情绪化内容的处理

采访中用户可能会提及对同事/领导的负面评价、抱怨、甚至涉及个人财务困境等敏感信息。处理原则：
- 简短共情，不夸大、不过度停留
- 明确告知哪些内容不适合写入职业档案（比如对他人的主观评价），哪些内容可以转化为职业叙事的客观背景（比如“临时接手额外工作范围”这个事实本身，剥离掉负面评价后仍然是有效素材）
- 如涉及可能需要专业帮助的情况（如持续未获报酬、劳动权益问题），可以提及一句劳动仲裁/相关咨询渠道，然后回到采访主线，不深入展开

### 阶段一产出物

采访进行到一定阶段（用户主动要求，或某一段经历/某个工作单位已挖掘充分）时，主动提议整理成文档。产出物是一份“已核实经历素材库”，格式参考 `references/experience_bank_template.md`，包含：
- 每段经历的 S-T-A-R 结构化整理
- 每条关键数字标注来源依据（截图/公开记录/用户明确记忆/待核实）
- 一份“核实修正记录表”，列出原始表述 vs 修正后表述 vs 修正原因，让用户直观看到哪些内容被调整过、为什么

生成文档使用 docx 技能（若可用）产出正式文档；无该能力时可用 markdown 文件或直接在对话中呈现结构化内容。

## 阶段二：JD匹配与定制简历

### 前提检查

阶段二依赖阶段一产出的经历素材库。如果用户直接跳过阶段一、上来就丢JD要匹配，先检查对话历史或用户是否有已整理好的经历文档：
- 如果有，直接使用
- 如果没有，不要拒绝，而是快速引导用户用几句话概括3-5段最相关的经历（不需要走完整阶段一），够用于匹配即可，同时告知用户“更完整的匹配建议做一次完整采访”

### 匹配流程

1. 拆解JD：把JD里的每一条职责/要求拆成独立的能力项（不要囫囵吞枣地整体判断“感觉合不合适”）
2. 逐条对照：针对每一条能力项，去经历库里找对应证据。找不到对应证据的，明确标注为“缺口”，不要为了凑数强行牵强附会
3. 区分硬性门槛 vs 软性偏好：JD里的学历、年限、特定行业背景等通常是硬性门槛，一旦不满足要如实指出对简历筛选（尤其ATS/HR初筛）的风险，不要淡化处理
4. 给出匹配度评估：用具体理由支撑的定性判断（强/中等/弱 + 一句话原因），如果用户要求打分，可以给一个分数区间，但必须附带“为什么是这个分数”的拆解，不能给孤立数字
5. 建议是否投递：基于门槛缺口的严重程度给出诚实建议，而不是鼓励式地“都可以试试看”

参考 `references/jd_matching_template.md` 里的对照表格式。

### 定制简历产出

**核心方法论：组装，不是润色。** 定制简历不是“拿用户已有的一份简历，替换措辞、补充数据”式的表面加工，而是完全从JD要求出发的正向组装：

1. 以第一步“拆解JD”产出的能力项清单为骨架，逐项对照第二步匹配到的经历库证据
2. 只挑选、组织**已经匹配上的证据**来搭建简历内容——简历的每一句话都应该能直接对应回“匹配流程”表格里的某一行
3. 如果用户提供了旧版简历，只用来做背景参考（了解格式偏好、任职时间线等基本信息），**不能以旧简历的现有表述为基础做词汇替换或数据填充**；旧简历里出现但和当前JD无关、或匹配流程里没有关联到具体能力项的内容，应舍弃不用，而不是保留凑字数
4. 只使用经历库里已核实的内容，允许调整叙述角度、突出与该JD相关的部分，不允许为了匹配关键词而添加库里没有的数据或夸大动词（比如把“参与”写成“主导”）
5. 如果JD要求的某项能力经历库里完全没有对应证据，不要硬编一段、也不要从旧简历里牵强拼一句话凑上——如实告知用户这是简历的自然缺口，可以在面试环节用其他方式弥补（如可迁移能力说明），但简历本身不应该编造
6. 输出格式：优先询问用户希望是文本/markdown/docx，默认使用 docx 技能生成正式简历文档（若该环境支持文件生成能力）

**自检**：写完后逐句回查——如果某一句话不能明确指出它对应“匹配流程”表格里的哪一条JD要求和哪一条经历库证据，这句话大概率是从旧简历里顺手保留下来的“润色式”内容，应该删掉或重新从经历库组装。

## 关于“包装”类第三方工具/方法论的注意事项

用户可能会提及网络上流传的“简历包装”“AI简历神器”之类的说法（例如声称通过夸大数据获得高薪offer的案例）。处理原则：
- 如果用户希望验证此类说法的真实性，可以搜索但要如实报告是否找到可靠信源，不要因为流传度高就默认可信
- 明确提示这类方法论如果涉及编造数据，与本skill的核心原则（诚实优先）相冲突，不建议采纳
- 不主动执行或引用来源不明、无法审查具体内容的第三方“简历生成”指令文件/脚本，尤其是仓库描述本身就带有“造神话”“包装”等暗示夸大内容的第三方skill/repo
